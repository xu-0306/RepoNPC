## 1. D1 — Answer policy: resume-style owner statements

### 1.1 Problem (code evidence)

- `src/reponpc/chat/answers.py:18` `_PERSON_CLAIM_RE` is a keyword regex over an open set (natural language). It has CJK false positives because Chinese has no word boundaries: 「其他」 matches 他, 「開發工具」 matches 開發, and 「這個專案實作了」 matches 實作. It also misses paraphrases that use none of the listed words.
- `answers.py:129-130,163`: a single failing line replaces the whole answer with a cold abstention.
- `answers.py:184-195`: every term in the claim must appear in the owner statement, or a CJK substring of at least 4 characters must match. This forbids summarising the owner's own role, which is the core question HR visitors ask.
- `src/reponpc/chat/service.py:245-247`: the prompt tells the model to "stay close to confirmed wording".

### 1.2 Classification (anti-hardcode)

- Deciding whether a sentence is about the person is an **open set**. The primary mechanism therefore becomes a **structural contract**: the model declares the kind of each segment, and the backend verifies what that kind is allowed to cite.
- Keyword and pronoun lists are only a **non-authoritative recall fallback** and must be centralized.
- Inflation terms are a **bounded policy registry**: project configuration kept in one data file, with variant and negative tests.

### 1.3 Envelope v2 (structured segments)

The provider returns this envelope instead of a free `answer_markdown`:

```json
{
  "segments": [
    {"kind": "person",        "text": "{{owner}} 負責後端 API 與部署流程。", "source_ids": ["S1"]},
    {"kind": "participation", "text": "{{owner}} 從 2024-03 到 2025-01 在這個專案有提交紀錄。", "source_ids": ["S4"]},
    {"kind": "project",       "text": "專案使用 FastAPI 與 SQLite 提供混合檢索。", "source_ids": ["S2", "S3"]},
    {"kind": "inference",     "text": "…", "source_ids": ["S2"]}
  ],
  "insufficient_evidence": false
}
```

- `kind` is a closed enum: `person | participation | project | inference`.
- `{{owner}}` is the **only** way for the model to refer to the portfolio owner. The backend renders it as `profile.display_name`. This anchor is structural and language-agnostic.
- Source markers move from inline text into `source_ids`. The backend renders the citation markers.
- `answer_markdown` from envelope v1 is accepted only through a legacy adapter for tests and migration. That adapter treats every line as `project` and applies the recall fallback in §1.5.

### 1.4 Per-segment validation rules

| Kind | Must cite | Additional checks |
|---|---|---|
| `person` | ≥1 `OWNER_ASSERTION` | Inflation check (§1.6) and numeric-fact check (§1.7). Paraphrasing is allowed. The rendered output carries a backend label: 「{owner} 自述」 / "In {owner}'s own words". |
| `participation` | ≥1 `PARTICIPATION` (§2) | The numeric-fact check applies to dates. It must not assert a role or responsibility; a segment that would need one must be `person`. |
| `project` | ≥1 `REPOSITORY_FACT` or repository metadata | Must not contain `{{owner}}` or an identity string. If the recall fallback detects a person reference, the segment is **reclassified** as `person` and revalidated. It is dropped only if that also fails. |
| `inference` | ≥1 non-inference source | The existing cycle rule is kept. It is rendered with the existing inference label. |

Envelope-level failures still reject the whole answer and produce the no-match reply (§1.8). These are invalid JSON or schema, model-authored URLs or HTML, unknown or unselected source IDs, and inference cycles. These are security or integrity failures, not content gaps.

### 1.5 Recall fallback (non-authoritative)

- **Identity registry:** built from `profile.display_name`, `profile.github_login` (new, §2) and optional `profile.aliases` (new, bounded list). It is derived from configuration, not code.
- **Per-locale person-reference lexicon:** a data file such as `src/reponpc/chat/policy/person_reference.<locale>.yml`. It holds pronouns and a CJK **exclusion-compound list** (for example 其他, 其它, 他人?). The ? marks an entry still to be decided by tests.
- The fallback can only **reclassify or drop a segment**. It never rejects the whole answer, and no rule depends on it alone.

### 1.6 Inflation lexicon

- This is a centralized registry, `src/reponpc/chat/policy/inflation_terms.yml`. It groups equivalent terms across locales, for example `{lead: [lead, led, 主導, 帶領, 領導]}`, `{founder: [founder, founded, 創辦, 創辦人]}`, `{senior: [senior, 資深]}`, `{sole: [sole, solely, single-handedly, 獨立完成, 一手]}`, `{architect: [architect, 架構師]}`, `{manager: [manager, managed, 管理, 主管]}`.
- **Rule:** if a `person` segment contains a term from a group, at least one cited owner statement must contain **some** term from the same group, in any locale. Otherwise the segment is dropped.
- Matching is normalized: casefolding for Latin text and NFKC normalization. For English, word-boundary matching with inflection variants is listed in the data file. For CJK, substring matching is used, and test cases prove the exclusions.
- This is intentionally a blocklist of **escalation** terms, not an allowlist of permitted wording.

### 1.7 Numeric-fact check (structural, closed form)

In `person` and `participation` segments, every number-like token must appear in a cited source after normalization. Number-like tokens include digits, percentages, years, dates, and CJK numerals where they are parseable. This blocks invented team sizes, metrics and durations without any word list.

### 1.8 Answering without owner statements, salvage and fallback (revised 2026-09-26)

Owners will not describe every part of their work, and asking them to do so is poor UX. A missing owner statement is therefore **normal, not a failure**:

- **Person-oriented questions without a matching owner statement** (for example 「他在這個專案做了什麼？」): the answer is built from `participation` segments and `project` segments. It says whose project it is and when they were active, then what the project does and how it is built. Example:
  > 這是王小明的個人專案，2024-03 至今有提交紀錄。〔GitHub 參與紀錄〕
  > 專案是一個 Next.js 作品集網站，文章以 Markdown 管理，部署在 Vercel，並串接 GitHub API 顯示專案資訊。〔專案文件與程式碼〕

  The answer does **not** contain "the owner has not explained this" or any other gap message for visitors. What is still not allowed is a `person` segment that asserts a personal role, responsibility or achievement ("王小明負責…", "主導了…") without an owner statement. Such a segment is dropped silently (reason code kept for §3).
- **Dropped segments:** if valid segments remain, they are shown as they are. **No visitor-facing "partially omitted" note** is appended. Reason codes go only to the owner's coverage check (§3).
- **Nothing relevant retrieved at all** (no valid segment, or `insufficient_evidence=true`): the NPC gives a short neutral reply and offers the suggested questions. The answer is not regenerated. Draft copy:
  - zh-TW: 「這個問題我在作品集裡找不到相關內容，可以試試下面這些問題。」
  - en: "I couldn't find anything about that in this portfolio. Try one of these questions."
  - The template adds up to three suggested questions and, if configured, the first profile link as a contact route.
- The NPC speaks as a guide **about** the owner (third person, `{{owner}}` rendered as the display name), never as the owner in first person, so visitors are not misled about who is answering.

### 1.9 Citation presentation

- By default, citations are grouped into one expandable **「來源 / Sources」** row with visitor-friendly labels: 「{owner} 自述」, 「GitHub 參與紀錄」, 「專案文件與程式碼」.
- Expanding a row shows the existing file, line and commit permalink details for engineers. Keyboard and screen-reader access must be preserved.

### 1.10 Prompt change (`service.py` policy prompt)

Replace the "stay close to confirmed wording / do not infer role" text with the following instructions:

- Classify every segment.
- Refer to the owner only as `{{owner}}`.
- Summarize owner statements faithfully without upgrading seniority, scope, or numbers.
- Never derive a personal role from code or participation facts. When no owner statement matches, describe what the project does and how it is built, together with participation facts.
- Use `insufficient_evidence=true` only when nothing relevant is retrieved.

## 2. D2 — `PARTICIPATION` evidence

- Add `EvidenceClass.PARTICIPATION` in `src/reponpc/domain/evidence.py`. This is an objective GitHub fact about the person, distinct from `REPOSITORY_FACT`.
- **Identity:** add a new `profile.github_login` config field. The admin UI prefills it from the configuration repository owner, and the owner must confirm it. Commits are matched only through GitHub's `author=<login>` filter. Commits made with emails not linked to the account are ignored, so the wording always means "at least / as visible on GitHub".
- **Facts per enabled repository, fixed at the pinned SHA:**
  - `is_repository_owner`: the repository owner login equals `github_login`.
  - `first_commit`: date plus immutable commit permalink.
  - `last_commit`: date plus immutable commit permalink.
  - `has_visible_commits`: boolean.
  - `other_contributors_visible`: boolean, from `GET /repos/{o}/{r}/contributors?per_page=2` (default branch; anonymous contributors excluded). Used only to choose between 「個人專案」 and 「{owner} 擁有、另有其他貢獻者的專案」 / 「有參與提交的專案」.
  - **No raw commit count** is stored for display.
- **Retrieval:** use `GET /repos/{o}/{r}/commits?author={login}&sha={pinned}&per_page=1`. The first page gives the latest commit. The `Link` header `rel="last"` page gives the earliest. - That is about 3 requests per repository, cached in the bundle.
  - Anonymous access is limited to 60 requests per hour.
  - An optional read-only token kept on the host may raise the limit; it is never exported.
  - If a request fails, the fact is recorded as **unavailable**, never as zero or "no participation".
- **Citations** point at the first and last commit permalinks, so they are immutable.
- **Display:** month granularity, for example 「2024-03 – 2025-01 有提交紀錄」 and 「專案擁有者」.
- Language breakdown remains a repository fact; it is not attributed to the person.

## 3. Pre-publish coverage check (supports D1 and D3)

- A standard question set lives in a registry file, per locale. It covers responsibility, what was built, duration, team or context, outcome and technologies.
- The check runs against the local build and reports, per question:
  - answered;
  - partially answered, with a list of dropped segments and reason codes;
  - no relevant content.
- The check is **informational, never a publishing gate**. Each gap offers an optional 「補一段自述」 shortcut, which opens the relevant claim editor with the claim `kind` preselected. Owners are not asked to describe every part of their work.
- The results feed the FAQ review queue (§4.3).

## 4. D3 + D4 — Public visitor page with live chat (MVP)

### 4.0 Target experience (owner reference mockup, 2026-09-26)

- Left: the owner's profile card (avatar, name, headline, bio, links) and project cards (name, description, language, stars, forks).
- Right: the animated pixel NPC with an online / resting indicator, a dialog box for **free-form questions**, suggestion chips, streamed answers and a collapsible 「來源」 citation list. The NPC is the owner's selected or uploaded character, and the scene around it follows that character (§4.4). The mockup's cat is only an illustration.
- The NPC is a **guide that talks about the owner in the third person** (「王小明的這個專案…」), not the owner speaking as 「我」 (§1.8).
- Mockup items **not** in the MVP:
  - **Views / traffic counts:** the GitHub traffic API needs a token with push access and covers only the last 14 days, so it is dropped. Stars and forks (public API) stay.
  - **Attachment button:** dropped; visitor uploads would add a new untrusted input path with no benefit for a portfolio.
  - **Microphone button:** post-MVP optional, using the browser Web Speech API only (no audio leaves the browser through RepoNPC).

### 4.1 Live chat transport (MVP, ADR-047 back in scope)

- Live answers run on the **owner's host**: the RepoNPC backend plus the owner's chosen chat model. Tailscale Funnel (ADR-047) exposes only the **visitor gateway** (public profile, projects, chat SSE, health). Admin routes and data stay private.
- All ADR-047 gateway requirements are MVP scope again: visitor-only route allowlist, rate limits and daily caps, request size limits, SSE timeouts, no credentials, and no host, model, provider or cost details in visitor responses. F0 (gateway split) and F2 (Funnel transport) return to the MVP plan.
- Consequence to communicate to the owner in the admin UI only: live answers exist only while the host and the model are running. Visitors never see this; they see the neutral resting state (§4.2).

### 4.2 Hosting topology (Q8, confirmed (b) 2026-09-26)

- **(b) Selected — static shell on GitHub Pages plus Funnel live API.**
  - 「匯出分享網站」 writes a self-contained folder (HTML/CSS/JS, JSON data, character assets, card images, `.nojekyll`, export manifest with hashes). The owner uploads it manually to their own repository (for example `<login>.github.io`). RepoNPC performs **no GitHub write**; the guide shows the steps with screenshots.
  - The page calls the Funnel visitor gateway for live chat. CORS on the gateway allows only the configured Pages origin, without credentials.
  - When the gateway is unreachable, the page stays up: the indicator shows 「休息中」, and typed questions are matched **in the browser** against the approved FAQ entries (question text plus owner-approved variants, lexical and fuzzy matching shipped as data; above a threshold the approved answer and its sources are shown, otherwise the nearest suggestions). Nothing is generated in the browser.
  - Export guards: public data only; secret scan; size check against GitHub Pages limits (1 GB published site, 100 GB per month soft bandwidth); no admin routes or data.
  - The export records the configured gateway origin; the page never embeds credentials, admin origins or host details. The existing same-origin visitor page served by the host remains available for local preview and for owners who choose an operator-managed gateway.
- **(a) Rejected** — whole visitor page served only through Funnel. Rejected because the shared link would show nothing while the host is off.
- The **GitHub card** links to the page URL entered by the owner, verified by fetching it and checking the export manifest hash.

### 4.3 FAQ review (D3)

- **Generation:** FAQ candidates come from `profile.suggested_questions` plus the coverage question set. They go through the same validated pipeline (§1).
- **Owner actions per item:**
  - approve;
  - reject;
  - regenerate;
  - 「改寫成自述」, which saves owner text as a claim and regenerates.

  Free editing of the answer text is **not** offered, because edited text would no longer be validated evidence (confirmed Q3).
- Approved FAQ entries serve as suggestion chips with instant answers and, in topology (b), as the offline fallback.
- Only `approved` items are exported or served. Approval is bound to the bundle ID; when the bundle changes, items become 「需要重新確認」.

### 4.4 Character-driven visitor scene (ADR-049, added 2026-09-26)

**Owner requirement (2026-09-26):** 「NPC角色與背景應該根據使用者上傳不同的角色而有所變化，這只是我使用貓咪角色的示意」. The cat in the reference mockup is only an example. The visitor page's NPC **and** its scene (background, NPC stage, accent colours, dialog tint) must follow whatever character the owner selects or uploads.

**Current gap (code evidence, 2026-09-26):**
- `CharacterRenderer` already draws any canonical sheet, so the NPC itself is not the problem.
- The page around it is fixed: the visitor CSS uses static `--ui-*` tokens and literal colours in `apps/web/src/styles.css`.
- `card.themes` only styles the GitHub card.
- The admin guide mascot (`.admin-workspace__npc`) is a CSS-drawn humanoid, not the owner's character.
- No configuration, API field or export artefact describes a scene.

**Classification (anti-hardcode):**
- **Open set:** characters are arbitrary (humanoid, animal, object, abstract, user art in any palette). A per-species theme table, a "cat theme", or branching on `pack_id`, filename or options is forbidden.
- **Closed set:** the scene *token roles* (below) and the precedence order are a fixed contract, like the seven animation states.

**Invariant:** for any valid canonical sheet (ADR-040), RepoNPC produces a deterministic scene in both light and dark themes. Every text pair meets WCAG 2.2 AA, and the NPC stays visually separable from its backdrop. The result depends only on the sheet's pixels plus explicit owner choices, never on names.

**Source of truth:** the canonical sheet. Built-in packs compile into the same sheet (ADR-039/040), so one derivation serves both modes.

**Resolution order (per token, first available wins; extended by the scene templates of §4.5):**
1. **Owner override** (explicit, in the character workspace):
   - an optional accent colour;
   - an optional background image.
2. **Pack scene hints:** a pack manifest MAY declare an optional scene provider. It is a pack-owned deterministic function of its own options returning a hue/accent hint and/or a backdrop PNG. Core treats it as opaque, and its output passes the same validation. `core/humanoid` declares none today, so it uses derivation.
3. **Derived from the sheet:**
   - Take the opaque pixels of all 28 frames (bounded: 256×448), convert them to OKLCH and cluster them by pixel share (median cut, at most 8 clusters).
   - The base hue comes from the dominant chromatic cluster.
   - The accent comes from the cluster with the highest chroma × √share.
   - If the chromatic share is below a fixed threshold, the scene is achromatic (neutral grey, not the old purple default).
   - The OKLCH lightness/chroma targets for each token role and theme live in **one** registry table.
4. **Neutral default:** used only when derivation raises an error (never silently for a valid sheet). The reason is reported to the owner.

**Token roles (closed set):**
- `background`, `surface`, `ink`, `muted_ink`, `accent`, `accent_ink`, `border`, `stage`, `glow`, `focus`.
- Each role exists for `light` and `dark` and is stored as `#rrggbb`.
- The frontend maps each role to a fixed `--scene-<role>` CSS variable through one mapping. Arbitrary property names or CSS strings from data are never applied.

**Contrast solver:**
- Before the tokens are accepted, the solver adjusts OKLCH lightness only (hue kept):
  - `ink`, `muted_ink` on `background` and on `surface`: ≥ 4.5:1;
  - `accent_ink` on `accent`: ≥ 4.5:1;
  - `accent`, `border` and `focus` against their neighbours: ≥ 3:1 (WCAG 1.4.11).
- **NPC separation:** the average colour of the sprite's edge pixels (opaque pixels adjacent to transparency) vs `stage` must reach ≥ 3:1. If `stage` cannot satisfy that together with the page constraints, `stage` becomes a contrasting plate behind the NPC rather than lowering text contrast.
- An owner accent that fails is adjusted, and the adjusted value is shown with a plain reason. It is never silently accepted, and never silently replaced without being shown.

**Background image (owner option):**
- Format and size:
  - PNG or WebP only;
  - no SVG, no animation;
  - at most 2 MB and 2560×1600, at least 640×360.
- Handling:
  - decoded with the existing bounded image guards and re-encoded server-side, with metadata stripped;
  - stored at `assets/scene/<name>.png|webp` (no nesting);
  - scaling is owner-chosen `smooth | pixelated`.
- Placement:
  - it is decorative (`alt=""`) and sits only behind the NPC stage and page margins;
  - text always sits on opaque `surface` panels, so contrast never depends on the image;
  - a theme scrim derived from `background` keeps dark mode legible.
- Without an image, the backdrop is the plain `background` colour with only the NPC stage drawn (revised by §4.5); there is no decorative pattern or species imagery.
- The upload flow, draft handling and preview are specified in §4.6.

**Configuration (additive, backward compatible):**

```yaml
character:
  scene:                      # omitted = automatic
    accent: null              # or "#rrggbb"
    background_path: null     # or assets/scene/<name>.png|webp
    background_scaling: smooth  # smooth | pixelated
```

- The scene is re-derived whenever the character sheet changes. Owner overrides persist across a character change, and the workspace then shows a notice with 「重設為自動」.
- `character.revision` versions the scene.

**Public output:**
- The profile gains `character.scene`, and the export writes the same object and backdrop file into the hashed manifest:

  ```json
  {
    "source": "owner|pack|derived|default",
    "revision": 3,
    "themes": {"light": {...roles}, "dark": {...roles}},
    "background_url": null,
    "background_scaling": "smooth"
  }
  ```

- New endpoint `GET /api/public/scene-background?rev=N`:
  - 404 when there is no image;
  - sends `nosniff` and an ETag.
- Tokens are computed in Python at validation/bundle time, never in the browser, so the live page and the Pages export render identically.
- The payload contains no host, model or cost fields.

**Owner UX (Character & animation workspace, new 「場景」 step):**
- A live visitor-page preview with the current character in light and dark themes, available and resting states, and reduced motion.
- The derived palette shown as labelled chips with its source (自動 / 角色包 / 自訂).
- A custom accent input, a background upload with preview, and 「重設為自動」.
- The admin guide mascot renders the active character through `CharacterRenderer`. The CSS mascot remains only as the no-character fallback.
- Admin chrome keeps its own neutral theme; only the preview is scene-themed.

**Out of scope:** animated backdrops, per-state scene changes, visitor-selectable themes, and automatic restyling of the GitHub card. `card.themes` stays explicit; the workspace MAY offer an explicit 「套用角色配色到卡片」 action.

### 4.5 Scene templates (ADR-050, added 2026-09-26, revised the same day)

**Owner requirements (2026-09-26):**
- 「背景以及配色可以提供幾套模板供使用者在設定時選擇」.
- Revision: 「範本背景如果只是程式畫的簡單圖形那不如不要」. Templates therefore carry **colour schemes only**. Pictures come from the owner's own background image (§4.6), not from programmatically drawn patterns.

**Classification (anti-hardcode):**
- **Closed set (project configuration):** the shipped templates. They live as data in **one** versioned registry, `scene_templates.yml`, packaged with RepoNPC and schema-validated at startup. It is the only place template values exist.
- **Closed set (code):** the palette modes and named tones below. A new template is data only.
- **Open set:** characters and owner images. A template MUST NOT reference a species, `pack_id`, filename or option key, and no code path branches on a template id. Every template must work with every valid character, with or without a background image.

**Invariant:** for every registry template and every valid canonical sheet, the resolved scene passes the §4.4 contrast solver and NPC-separation check in both themes. Template choice changes colours, never accessibility.

**Registry entry (schema):**

```yaml
templates:
  - id: night               # stable, [a-z0-9_]+
    version: 1              # bumped whenever values change
    label: {zh-TW: 夜空藍, en: Night blue}
    palette:
      mode: fixed           # follow_character | fixed
      hue: 268              # fixed only: OKLCH base hue in degrees
      accent_hue: 85        # fixed only: OKLCH accent hue in degrees
      tone: deep            # key into the single per-role L/C target table
aliases: {}                 # retired id -> successor id (compatibility shim)
```

- Colours are OKLCH hue seeds plus a `tone` reference, never hex or CSS. The lightness/chroma targets for each role stay in the one §4.4 target table, which gains named tones: `standard`, `soft`, `deep`, `vivid` and `neutral` (chroma 0).
- `follow_character` takes the base and accent hue from the character (pack hint, then derivation, then neutral default, per §4.4). `fixed` uses the template's hue seeds.
- Both themes (light and dark) are produced for every template.
- Validation rejects the registry at startup on any of:
  - a duplicate or malformed id;
  - an unknown mode or tone;
  - a hue outside 0–360;
  - a missing label locale;
  - an alias cycle or dangling alias;
  - any unknown field, which includes backdrop, pack, species or CSS fields.

**Starter set (drafted, owner may change):**

| id | zh-TW label | Palette |
|---|---|---|
| `auto` | 自動（跟隨角色） | follow_character, `standard` (the §4.4 behaviour) |
| `soft` | 柔和（跟隨角色） | follow_character, `soft` |
| `warm` | 暖陽橘 | fixed: warm amber base, coral accent, `soft` |
| `night` | 夜空藍 | fixed: deep indigo base, gold accent, `deep` |
| `forest` | 森林綠 | fixed: green base, amber accent, `standard` |
| `mono` | 黑白簡約 | fixed, `neutral` |

**Backdrop without an owner image:** the plain `background` colour plus only the NPC stage (a soft floor shadow, and the plate when the solver needs it). No decorative patterns, drawn shapes or species imagery. A pack backdrop hint (§4.4) is still honoured when present.

**Illustrated template backgrounds:** not in MVP. A future template MAY reference a bundled illustrated image only with a recorded licence, and that image passes the same validation as an owner image (§4.6).

**Resolution order (replaces the §4.4 list; per token, first available wins):**
- **Palette:**
  1. owner accent override (accent roles only);
  2. the selected template's fixed hue seeds, when `mode: fixed`;
  3. the character hue: pack scene hint, then sheet derivation;
  4. neutral default, only on derivation error, with the reason shown.
- **Backdrop:**
  1. owner background image (§4.6);
  2. pack backdrop hint;
  3. the plain `background` colour.
- The contrast solver and NPC-separation check (§4.4) run last, on the resolved tokens. When the stage cannot separate from the character, the stage plate appears. The template's text contrast is never lowered.

**Configuration (additive; omitted = `auto`):** `character.scene.template` holds a registry id; see §4.6 for the full block.
- An unknown id fails closed: config validation reports it and lists the valid ids, and the last published bundle keeps serving.
- A retired id resolves through `aliases`, and the workspace shows the successor.
- The template choice persists across character changes. `follow_character` templates re-derive from the new character automatically.

**Public output:**
- `character.scene` gains `template: {id, version}`, and `source` also accepts `template`.
- The export manifest stores the **resolved** tokens, so a later registry change does not alter a published site until the next export.
- Visitors cannot pick templates. Frontend source contains no template id; the §4.4 style guard also fails on template ids.

**Owner UX (「場景」 step, colour part):**
- A template gallery as a keyboard-operable radio group, labelled 「跟隨角色配色」 or 「固定配色」.
- Each tile is a miniature of the visitor page rendered live with the **active character** and the current (or draft) background image, through the same components as the §4.6 preview. Tiles are not static screenshots.
- Selecting a tile updates the large preview; saving is explicit.
- If a fixed template needed a stage plate or solver adjustment for this character, a plain notice says so.
- 「重設為自動」 restores `template: auto` and clears the overrides.
- Onboarding: the default `auto` needs no choice, and the novice flow can skip this step.

### 4.6 Owner background image with a realistic preview (ADR-050, added 2026-09-26)

**Owner requirement (2026-09-26):** 「可以補上自己上傳背景圖的功能，並要有預覽讓使用者能看到套用上背景圖與角色後大概會是什麼樣的介面」. The owner background image is **MVP scope**; this resolves the Q10 assumption. Before anything is published, the owner sees what the visitor page will look like with that image and the active character.

**Invariant:** the preview and the published page render from the same components and the same server-resolved scene. For equal settings, what the owner approves is what visitors get. Nothing public changes until the owner presses 「套用」.

**File rules:** as in §4.4 "Background image": PNG or WebP only, no SVG or animation, ≤ 2 MB, 640×360 to 2560×1600. Files are decoded under the existing bounded image guards and re-encoded with metadata stripped.

**Flow in the 「場景」 step:**
1. **Choose:** a file picker plus a drag-and-drop area, with the rules shown in plain language before upload.
2. **Draft:** the server validates and re-encodes the file into a private **draft**.
   - The draft is stored in runtime data, not under `assets/`, and is never publicly reachable.
   - There is at most one draft per owner session; a new upload replaces it. Drafts expire after 24 hours and on 「取消」.
   - A rejected file gets a plain-language reason (for example 「圖片太大，請小於 2 MB」 or 「不支援 SVG」), and nothing is stored.
3. **Preview:** a visitor-page preview built from the real visitor components in a preview mode, showing:
   - the draft image as the backdrop;
   - the active character, animated, on its stage;
   - the header with the owner's display name;
   - a sample dialog: one localized sample question and answer, visibly marked 「範例」, with sample suggestion chips and the input bar. No provider call is made, and the sample text never comes from the model.

   Controls:
   - 淺色 / 深色;
   - 桌面 / 手機 frames (a desktop frame and a phone frame, scaled to fit);
   - NPC state: 待機 / 說話 / 休息中;
   - reduced motion;
   - 套用前 / 套用後, to compare with the currently published scene.
4. **Adjust** (every change updates the preview immediately):
   - **Focus point:** click or drag on the image thumbnail, or use the arrow keys. It sets which part stays visible when the image is cropped. The thumbnail outlines the desktop and phone crop areas at the same time.
   - **Dim:** `auto | none | low | medium | high`. This is a scrim derived from `background` that calms busy images. `auto` picks the lowest level at which the NPC-separation check passes without a stage plate, and falls back to the plate when no level passes.
   - **Scaling:** `smooth | pixelated`; `pixelated` is suggested for pixel art.
   - The selected template's colours apply on top.
5. **Notices** (plain language, non-blocking):
   - the image is smaller than the desktop frame and will be enlarged (blurry), with a suggestion to use `pixelated` for pixel art;
   - the aspect ratio differs strongly from the desktop or phone frame, so a large part is cropped;
   - the image is busy behind the NPC, so dimming or the stage plate was applied.
6. **Decide:**
   - 「套用」 promotes the draft to `assets/scene/<content-hash>.png|webp`, saves the settings and bumps `character.revision`. The next export includes it.
   - 「取消」 discards the draft and changes nothing.
   - 「移除背景圖」 returns to the plain template background, previewed the same way.

**Configuration (additive; omitted fields use the defaults shown):**

```yaml
character:
  scene:
    template: auto              # registry id (§4.5)
    accent: null                # or "#rrggbb"
    background_path: null       # or assets/scene/<name>.png|webp
    background_scaling: smooth  # smooth | pixelated
    background_focus: {x: 50, y: 50}  # percent, 0–100
    background_dim: auto        # auto | none | low | medium | high
```

**Admin API (authenticated session; mutations also require CSRF):**
- `POST /api/admin/assets/scene/background-drafts` (multipart): validates and re-encodes. Returns `{draft_id, width, height, format, notices[]}` or a plain-language error.
- `GET /api/admin/assets/scene/background-drafts/{id}`: the draft image; owner-only, `Cache-Control: no-store`, `nosniff`.
- `DELETE /api/admin/assets/scene/background-drafts/{id}`: discards the draft.
- `POST /api/admin/scene/preview`: takes proposed settings (`template`, `accent`, `background: draft:<id> | current | none`, `focus`, `dim`, `scaling`). Returns the resolved scene in the same shape as the public `character.scene`, plus notices. It persists nothing.
- `PUT /api/admin/scene`: applies the settings and promotes a referenced draft.

**Public output:**
- `character.scene` gains `background_focus` and `background_dim` next to `background_url` and `background_scaling`.
- The public image stays at `GET /api/public/scene-background?rev=N`, which never serves drafts.
- The frontend applies focus as `object-position` and dim as a scrim from the `--scene-background` token. It reads no other image metadata.

**Accessibility:**
- The image stays decorative (`alt=""`).
- Text always sits on opaque `surface` panels, so contrast never depends on the image or the dim level.
- The focus control is keyboard-operable and announces its position.

## 5. D5 — Windows-first novice installer

- **Packaging (confirmed Q6):** the UI is a web GUI in the browser, so no desktop shell (Electron/Tauri) is needed.
  - **PyInstaller in onedir mode** bundles Python, locked dependencies (including `onnxruntime` and `uvicorn`, both covered by `pyinstaller-hooks-contrib`) and the prebuilt web assets.
  - onedir, not onefile: faster start (no temporary extraction on every launch) and fewer antivirus false positives.
  - An **Inno Setup per-user installer** (no admin rights) wraps the folder, creates Start-menu and desktop shortcuts and an uninstaller.
  - The launcher starts the backend on localhost, waits for health, then opens the admin UI in the default browser; a tray icon or small console offers 「開啟管理頁面」 and 「結束」.
  - The bge-m3 model is **not** bundled (§6.2).
- **Docker** remains the path for Linux, servers and advanced users. **macOS** is out of scope for the first release.
- **Unsigned MVP:** the download page explains the SmartScreen prompt 「其他資訊 → 仍要執行」 with screenshots, and publishes SHA-256 checksums.
- **Uninstall** keeps user data unless the user explicitly chooses removal.
- **MVP updates** are done by downloading the new installer, which preserves the existing data (user data lives outside the install folder).

## 6. D6 — Built-in embedding default

### 6.1 Spec conflict — explicit supersession required

The following current text must be amended:

- `TECHNICAL_SPEC.md` §5.4: "There is no RepoNPC-local production embedding default…"
- §13.3: the local adapter "MUST NOT be advertised as the default".
- FR-006: "configured external multilingual embedding profile".
- FR-012: the sentence-transformers restriction.

Proposed replacement: a **built-in ONNX embedding adapter** (`builtin_onnx`, CPU, ONNX Runtime, no PyTorch) is the production default for new portfolios. The existing `openai_compatible` and `ollama` embedding adapters remain selectable in Settings. The sentence-transformers adapter keeps its fixture-only status.

### 6.2 Contract

- **First-use choice (confirmed Q1):** the first time an index is needed, a dialog offers three options:
  - 「下載內建模型（約 570 MB）」: shows the size, the license and the source, then a progress bar with cancel and resume. The download is verified against a pinned checksum.
  - 「改用其他 embedding 服務」: opens the existing Ollama or OpenAI-compatible embedding setup.
  - 「稍後再說」: nothing is downloaded. Building stays blocked, with the reason explained, until one of the two options above is completed.

  Nothing is downloaded without that click. The model is not bundled in the installer.
- **Identity:** the model ID, revision hash, dimension and prefixes are recorded in the bundle exactly as today. Changing the embedding model requires a full re-index, and the UI states this before the user confirms.
- **Source pinning:** prefer an official ONNX export or a RepoNPC-produced conversion with a pinned hash. Third-party quantized uploads are not a trusted default source.

### 6.3 Candidates considered (decided Q1)

| Model | int8 ONNX size | Dim | Context | zh quality | License* | Notes |

| multilingual-e5-small | ~118 MB | 384 | 512 | weakest | MIT | Needs `query:`/`passage:` prefixes; best for low-RAM hosts |

| Qwen3-Embedding-0.6B | ~560–640 MB | ≤1024 | 32K | best (C-MTEB 66.33 overall, 71.03 retrieval) | Apache-2.0 | Needs query instruction; naive int8 quantization loses quality |

- The other two models stay available only through the "other embedding service" path, for example by running them in Ollama. They are not additional built-in downloads in the MVP.
- Before release, bge-m3's retrieval quality is measured on the zh-TW/en fixtures to catch regressions against the current external profile. That measurement does not reopen the choice.

## 7. D7 — Chat model guidance (owner scope confirmed 2026-09-26)

The owner connects their own model. RepoNPC must never choose or switch providers silently. All guidance in this section is shown **only in the owner's admin UI**. Visitors see only whether the NPC is available (§4). They never see host uptime, provider, cost or hardware information.

**In scope:**

1. **Device check and model suggestions.**
   - Detect the host's RAM, GPU and VRAM, and free disk space on the host side through the local backend, not the browser.
   - Compare the results against a RepoNPC model catalog data file, `model_catalog.yml`. Each entry records the parameter count, available quantizations, estimated memory, whether structured JSON output is supported, and a "last reviewed" date.
   - Show each model as 「適合 / 勉強可用 / 不建議」. The memory estimate uses the same public method as canirun.ai: parameters × bits per weight, plus overhead. The speed estimate uses memory bandwidth.
   - Show a link 「在 canirun.ai 查看更多模型」, prefilled with the detected hardware where the site supports it.
   - canirun.ai's data is **not copied**: its repository `midudev/canirun.ai` has no license file. RepoNPC also does not call its API automatically, because that would send the hardware profile to a third party.
   - The catalog lists only models that RepoNPC's answer envelope has been tested against, because small models often break the JSON format.
2. **Local runtime helper (Ollama and similar).**
   - Detect whether the runtime is running and list the installed models.
   - Show the download size from the catalog.
   - The pull starts only after an explicit click and shows progress.
3. **Plain-language error mapping.** Map provider probe failures to a cause and a next step: runtime not running, model not downloaded, out of memory, wrong key, rate limited, timeout, unsupported response format.
4. **One-line status summary** in the admin UI, for example 「目前使用：本機 Ollama · qwen3:8b」 or 「雲端 · {provider} · {model}（依用量計費）」.
5. **Data disclosure** when a cloud chat or embedding provider is selected: 「送出的內容：訪客問題與作品集中公開的片段；不包含金鑰、管理資料或未公開檔案」.

**Deferred** (not in MVP): readiness test (試答測驗) and cloud cost estimate. The existing chat-model probe (FR-038/040) remains the MVP compatibility check.

## 9. Test plan highlights (anti-hardcode)

- **Answer policy:**
  - The same claim is paraphrased in zh-TW and en, and both pass.
  - An inflated variant of each (「主導」 / "led", when the owner only said 「參與」 / "contributed") drops only that segment.
  - An invented number drops the segment.
  - Negative cases: 「其他功能」, 「開發工具」 and 「這個專案實作了…」 in `project` segments are **not** treated as person claims.
  - A project segment containing the owner's display name or alias is reclassified and validated.
  - Envelope-level injection (URL, HTML, unknown ID) still rejects the whole answer.
  - Zero valid segments produces the no-match reply with no provider retry call.
  - A person question with only code and participation evidence yields project + participation segments, contains no gap/"not explained" wording, and contains no personal-role assertion.
  - Dropped segments produce no visitor-facing note; reason codes appear only in the coverage report.
- **Registry tests:** every inflation group has zh-TW and en entries. The lexicon files load and are the only source; no duplicated literals appear in code.
- **Participation:**
  - Pagination with and without a `Link` header.
  - A single-commit repository.
  - No commits by the login.
  - A 403 or rate-limit response produces an unavailable fact.
  - The pinned `sha` parameter is honoured.
  - An organization-owned repository gives `is_repository_owner=false`.
  - A repository with a second contributor gives `other_contributors_visible=true`.
- **Visitor gateway:** admin routes return 404 through Funnel; visitor responses and error bodies contain no host, model, provider or cost fields; rate limit and daily cap enforced.
- **Character scene (§4.4):**
  - Fixtures are generated programmatically and deliberately include no cat:
    - a non-humanoid blob or object;
    - a monochrome grey sprite;
    - a near-white and a near-black sprite;
    - a single saturated hue;
    - a multi-hue sprite;
    - a sprite whose dominant colour equals the old default background;
    - the `core/humanoid` pack with two different colour options.
  - Assert:
    - distinct palettes give distinct token sets, and the base hue follows the dominant hue within tolerance;
    - an achromatic sprite gives a neutral scene;
    - every contrast pair and the NPC-separation check pass in both themes;
    - identical input gives byte-identical tokens.
  - Name independence: renaming the sprite file or changing option *key names* in a test pack with identical pixels leaves the tokens unchanged. No code path reads `pack_id`, filenames or option keys for scene decisions.
  - A failing owner accent is adjusted and reported.
  - Background upload rejects SVG, animated, oversized, undersized and polyglot files, and strips metadata.
  - The export contains the same tokens and a hashed backdrop, and renders with the host stopped.
  - A style guard fails if visitor CSS contains literal colours outside the single neutral-default token block.
- **Scene templates (§4.5):**
  - Matrix: every registry template × every character fixture above × light/dark × (no image, a busy photo, a flat image) passes the contrast and NPC-separation checks. It includes a sprite whose dominant colour equals a fixed template's background, which must trigger the stage plate rather than lower text contrast.
  - Registry-driven: a test-only registry with an invented id and labels renders end to end with no code change; removing a template from the test registry removes it from the gallery.
  - Fail closed: an unknown configured id is rejected with the valid list, and a retired id resolves through `aliases`. A registry with an unknown field (including any backdrop field), mode, tone or locale, a hex colour, a hue outside 0–360, or an alias cycle fails to load.
  - Behaviour: a `follow_character` template gives different tokens for two different sheets; a `fixed` template keeps its hue seeds across sheets. Without an owner image no decorative pattern is drawn.
  - Guards: no source file outside the registry contains template values; frontend source contains no template id.
  - The export stores resolved tokens plus template id and version, and identical inputs give identical manifests.
- **Owner background image and preview (§4.6):**
  - Upload creates a private draft: the draft URL requires the owner session, sends `no-store`, and is never reachable through public routes, `scene-background` or the export until 「套用」.
  - Rejections (SVG, animated, oversized, undersized, polyglot, wrong extension/content) give plain-language reasons and store nothing; accepted drafts have metadata stripped.
  - A second upload replaces the draft; 「取消」 and 24-hour expiry delete it; 「套用」 promotes it to a content-hashed file and bumps `character.revision`.
  - Preview parity: for the same settings, `POST /api/admin/scene/preview` and the published profile return identical scene objects, and a browser check compares computed styles of the preview frame and the live visitor page.
  - The preview uses the active character (tested with two non-cat fixtures), shows the sample dialog marked 「範例」 and makes no provider call.
  - Focus moves the visible crop in both desktop and phone frames; `dim: auto` picks the lowest passing level or the plate; notices appear for small, strongly cropped and busy images.
  - Keyboard-only and screen-reader checks cover the upload, focus control, frame and theme toggles, and apply/cancel, in both locales.
- **Static export (topology b):**
  - The site renders with the RepoNPC host stopped.
  - Unapproved FAQ entries are absent.
  - No admin paths or secrets appear in any exported file.
  - The manifest hash is verified.
